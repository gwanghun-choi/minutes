# 2026-08-24

## Goal

Three independent gaps, closed without letting them touch each other's
responsibility, API, or tests.

1. Uploading the same recording twice re-ran the whole analysis and left two
   meetings to tell apart by hand.
2. AI 후보정 repaired grammar around a mis-heard word instead of the word.
   The UAT case: `여보세요? 네, 전화를 받습니다.` / `네, 안녕하세요. 혹시 턱
   되실까요, 잠깐?` / `네.` came back as `혹시 턱 괜찮으실까요` — fluent, and
   nonsense for a call that has just connected.
3. Every folder in the sidebar had a count beside it; 전체 회의 and 미분류, the
   two rows above them, had nothing.

## Completed

### A. The same file, uploaded twice, is one meeting

Identity is `(owner_user_id, SHA-256 of the original bytes)` — see
[the decision record](../decisions/2026-08-24-duplicate-uploads-are-owner-scoped-by-content-hash.md)
for why it is owner-scoped and why the hash is not global.

- **Migration 012** adds `meetings.source_content_hash` (nullable, `CHECK` for
  64 lowercase hex) and a partial unique index on the pair,
  `WHERE source_content_hash IS NOT NULL`. Additive; nothing is backfilled, so
  every existing meeting keeps a NULL hash and takes part in no comparison.
- **The digest rides the write loop.** `create_meeting` already streamed the
  body a megabyte at a time; `hashlib.sha256().update(chunk)` goes in the same
  pass. No whole-file read, no second pass over the disk.
- **The check lands before the row.** Lookup → on a hit, `unlink` the file just
  written and answer `409`. No meeting, no version, and no `BackgroundTasks`
  entry: a guard that ran after `pipeline.process` was queued would have saved
  nothing, which is the whole point of the feature.
- **The index is the guarantee.** Two uploads that both pass the SELECT race to
  insert; the loser's `UniqueViolation` is caught and becomes the same 409
  rather than a 500.
- **409 body:** `detail` (worded by the existing meeting's status),
  `code: DUPLICATE_MEETING_SOURCE`, `existing_meeting_id`,
  `existing_meeting_title` (this account's own alias, via
  `organization.DISPLAY_TITLE`), `existing_meeting_status`. No hash, no path.
  `FAILED` is refused too and says to delete the meeting first; deletion is a
  hard `DELETE`, so it frees the bytes.
- **Frontend:** `ApiError` now carries the parsed error body, and the upload
  dialog turns a duplicate into the server's sentence plus a 기존 회의 보기
  button. Every other caller still reads `detail` alone. Upload stays one file
  at a time — no batch endpoint.

### B. 후보정 is context-aware post-correction, not proofreading

Root cause: the old prompt sent `"<번호>: <문장>"` with no speaker and no clock,
and its rules were "STT 오인식, 띄어쓰기, 명백한 용어 오류만" plus **"의미를
바꾸지 마세요"** — which is exactly the instruction that preserves `턱` and
repairs the grammar around it. Nothing said the token itself could be the error,
nothing asked whether the fix survived the reply, and nothing made abstaining an
outcome.

- **`assist._render_for_correction`** renders every utterance as
  `<번호> [mm:ss~mm:ss] <화자>: <문장>` in time order, reusing `rag._fmt_time`.
  Still one request for the whole meeting: every line therefore arrives with the
  line before and after it and the turn boundary between them, and a windowed
  call per segment would multiply an OpenAI request by the length of the
  recording for context this rendering already gives away.
- **`CORRECTION_PROMPT` rewritten** around three claims: the ASR token itself may
  be wrong (`기존 단어를 무조건 보존하지 마세요`); a fix must hold against the
  previous turn, the reply, and the topic, not just grammar; and abstaining is
  the default. Plus: no rewriting of 말투, no synonym swaps, no invented
  information, never flip negation or possibility, and a named conservative list
  (names, companies, products, numbers, amounts, dates, deadlines, places, terms,
  requests, decisions, assignees).
- **A correction must say why.** Each suggestion carries `reason`, and
  `suggest_corrections` drops any that arrives without one — the abstention rule
  enforced rather than trusted. Also dropped: an unknown sequence, a
  non-numeric sequence, unchanged text, and a second suggestion for a sequence
  already proposed.
- **HITL semantics unchanged.** Suggestions write nothing; 개별 반영 and 모두
  반영 edit the draft in the browser; only 수정 내용 저장 (the existing PATCH)
  persists; `_editable_draft` still gates the endpoint. 모두 반영 is safe
  because there is no uncertain tier in the response — an uncertain suggestion is
  simply not returned.
- **Frontend:** each card shows the reason under the before/after, and the empty
  state says why there is nothing rather than implying a failure.

### C. 전체 회의 and 미분류 carry counts

- **`organization.UNFILED`** is 미분류 as one predicate — the absence of a
  *categorised* filing, so an alias with no folder still counts as unfiled.
  `meetings._narrow` now pastes it instead of holding its own copy, which keeps
  the sidebar count and the `?category=none` page describing one set.
- **`organization.NAV_COUNTS`** is one aggregate over `access.READABLE`:
  `total` and `uncategorized`. `GET /api/meeting-categories` returns
  `{categories, total, uncategorized}` — two aggregate statements on one
  connection, neither growing with the tree.
- **Semantics left alone.** A folder's `meeting_count` is still *direct*
  membership, matching the rows the tree draws under it; the list page still
  means the subtree. Both counts are taken through `access.READABLE`, so a
  PENDING, REJECTED, or REVOKED share counts for nobody and another account's
  meeting is invisible in the number as well as on the screen.
- **One `Count` component** in `CategoryNav`, shared by all three kinds of row:
  same typography, same column, zero not drawn — the rule the tree already had
  for an empty folder, applied to the two fixed rows rather than a second rule
  beside it. Past 99 the label is `99+` (`lib/format.ts:countLabel`) and only
  then does the row carry a `title` with the real figure. Nothing truncates the
  count itself.
- **Invalidation.** Upload and delete now invalidate `keys.categories` as well
  as `keys.meetings`; filing, category CRUD, and accepting an invitation already
  did.
- Route state, `aria-current`, direct meeting placement, and `descendants=0` are
  untouched; the count is metadata inside the row's link and does nothing of its
  own.

  must not confidently propose an incoherent fix. Whether a real completion says

  pin the prompt and the validation instead.
