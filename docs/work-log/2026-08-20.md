### HITL transcript review gate — this session

Split the pipeline at an explicit human approval boundary. Analysis now ends at
`REVIEW_REQUIRED`; chunking and embedding moved into `pipeline.index_transcript`,
which only `POST /api/meetings/{id}/approve` starts. Indexing re-reads the
transcript from the database, so reviewer corrections — not the AI draft — become
RAG evidence.

- One new status value, `REVIEW_REQUIRED`. `INDEXING` was reused for the approval
  phase. `status` is plain `TEXT`, so **no schema change was needed**.
- Approval is an atomic `UPDATE … WHERE status = 'REVIEW_REQUIRED'`; a repeated
  approval matches no row and returns `409`.
- Indexing failure returns the meeting to `REVIEW_REQUIRED` with the error in
  `error_message`, leaving the transcript intact and retryable.
- New: `PATCH /api/meetings/{id}/transcript` (bulk segment text + speaker
  reassignment, rejected outside the gate). The existing per-speaker rename route
  was reused unchanged.
- `_persist_transcript` now upserts `speakers` instead of deleting them, so a
  reviewer's `display_name` survives a redraft.
- `rag.search` gained `AND m.status = 'COMPLETED'` as defence in depth.
- The meeting detail page doubles as the review screen: editable rows, a speaker
  select per segment, and separate 저장 / 승인 buttons. Approve always saves first
  so unsaved edits cannot be silently dropped.

Final hardening before commit, after re-reading the source for semantic gaps:

- **Speaker rename was not gated server-side** — it worked on `COMPLETED`
  meetings, protected only by a disabled UI input. Now restricted to
  `REVIEW_REQUIRED` via an `EXISTS` predicate inside the `UPDATE`. An approved
  transcript is uniformly immutable; without this a rename could make
  `chunks.content` ("화자 A: …") disagree with the source label ("김팀장").
- **Edit could race an approval** — `edit_transcript` read the status and wrote
  segments in the same READ COMMITTED transaction, so an approval could commit in
  between and the edit would miss the index while the meeting reported
  `COMPLETED`. Now `SELECT … FOR UPDATE`. Verified with two concurrent
  connections: the approval blocked 1.5 s until the edit committed, then indexed
  the edited text.
- **Legacy `COMPLETED` rows** — investigated, no code or data change. See below.

## Meeting deletion — this session

### Goal

Delete a meeting and every piece of application-owned data it holds — its rows,
its chunks and embeddings, and both audio files — without touching any other
meeting or schema.

### Completed

- `DELETE /api/meetings/{id}`. One `DELETE FROM meetings WHERE id = %s AND
  status = ANY(%s) RETURNING stored_filename` does the whole database side: all
  three child tables are already `ON DELETE CASCADE` in `scripts/init_db.sql`,
  so no child delete was written. The status predicate is inside the statement,
  so it cannot be raced.
- Files: `audio.meeting_files(stored_filename)` returns the original and the
  `.16k.wav`. It lives beside `to_wav16k` so the suffix rule has one home — a
  deletion that re-derived it separately would leak files the day it changed. It
  reduces the name to `Path(...).name` and requires the parent to be
  `UPLOAD_DIR`, so nothing outside the upload directory is reachable, and it
  returns only files that exist, which makes a missing file a non-event.
- Order is database first. A failed unlink leaves an unreferenced file; the
  other order would leave a meeting row pointing at audio that is gone. An
  unlink that fails is logged, not raised — the meeting really is deleted, so
  reporting failure would be a lie.
- Deletion is refused outside `REVIEW_REQUIRED`, `COMPLETED`, `FAILED`. Tracing
  `pipeline.process` showed why: the foreign keys stop a mid-flight task from
  writing orphan rows, but `to_wav16k` can recreate the normalized WAV after the
  delete, leaving a file nothing refers to. `UPLOADED` is refused too, because
  `process` is already scheduled by the time that row exists. No cancellation
  system was built.
- UI: one `회의 삭제` button beside 재임베딩, shown in the same settled states,
  native `confirm()`, then navigate to the list. One CSS line for the danger
  colour, matching the existing per-button overrides.
- No new dependency, table, column, status, or service module.
